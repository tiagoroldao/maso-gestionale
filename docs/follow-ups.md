## Not yet issues

- **Sending a Quote while it is saved is untested under concurrency** (#137): `Quotes.send` and `Quotes.save` both lock the Job, then the Quote, so a save racing a send either lands before it or is refused. Tests share one connection, where locks are re-entrant, so none proves it; test it on separate connections with the other locking tests (#19).
- **Quote numbers untested under concurrency** (#138): `Quotes.create` takes the Job's next Quote number under the Job's lock, and `(job_id, sequence)` is unique, so two Quotes written at once get different numbers or one fails. Tests share one connection; test it with the other locking tests (#19).
- **A sent Quote on a cancelled Job stays "Inviato"** (#138): when Office cancels the Job before recording the Customer's "no", the Quote can no longer be decided, so it reads as still waiting (the Jobs list's "waiting for an answer" filter leaves cancelled Jobs out). Consider allowing a decline, only, on a cancelled Job.
- **A draft Quote can't be deleted** (#138): with several Quotes per Job, a draft started by mistake stays on the Job (and keeps its number); declining it is the only way to set it aside. Add a delete for drafts never sent if it happens in practice.
- **Rolling back #138's migration** (`1761885935215_several_quotes_per_job`): refused while a Job has several Quotes. Otherwise the Job statuses are worked out again from the Quote (quoted, accepted), but a Job whose Quote was declined stays open rather than cancelled, and an accepted Job whose only work Visit is past becomes in progress.
- **Quote statuses on the Customer and Site pages** (#138): only the Jobs list shows each Job's Quotes and filters by them; the Customer and Site pages' Job lists show the Job status alone.
- **Customer's role at a Site** (owner, administrator, tenant): a domain question raised in the #43 review; decide during the UX pass or when a feature needs it.
- **Archived-reference check outside the lock:** Quote and Invoice saves read which archived Items and VAT Codes the record already uses before locking it, so a concurrent save or archive could let an archived reference onto a draft. Move the check inside the locked transaction for both (from the #77 review); likewise `Invoices.create` checks an archived Customer only in the validator (harmless: Invoices don't block archiving) (from the #95 review).
- **Closing a Visit by mistake (#16):** "Done" and "needs another visit" are final; neither the Technician nor Office can reopen a Visit. Accepted trade-off for now; revisit if it happens in practice (an Office "reopen" that reverses the stock usage).
- **Invoice PDF logo:** finalised Invoices (and sent Quotes, #137) copy the company's details, but the PDF still uses the current logo from Company settings, so changing the logo changes old PDFs (from the #82 review). Copy the logo file reference at finalising if this matters.
- **pg deprecation warning in tests:** "client.query() when the client is already executing a query" appears in functional tests (field work, dev seeder) under the global transaction: some code path runs queries in parallel on one connection. Find it with `node --trace-deprecation` before the pg 9 upgrade.
- **Dev seed timing:** the seeder starts today's boiler Visit (09–13) whatever the time, so seeding early or late gives an in-progress Visit outside its hours. Harmless. Its test can also fail if midnight passes between seeding and loading My Visits (milliseconds; no action).
- **Release image is amd64 only** (#36): add `docker/setup-qemu-action` and `platforms: linux/amd64,linux/arm64` if the server turns out to be ARM (ADR 0002: whatever hardware the business owns) (from the #100 review).
- **`latest` follows the newest tag pushed** (#36): a hotfix on an older line (`v1.0.1` after `v1.1.0`) moves `latest` back. Only matters once old lines get patches; pin `APP_VERSION` meanwhile (from the #100 review).
- **Concurrent equipment removal untested:** `FieldWork.removeItem` locks the equipment it created before checking whether another line or Visit uses it. Only reading the code checks this; no test runs two connections against it (from the #98 review).
- **Charge history deletes** (#114): the `charge_events` trigger blocks updates only. Deletes stay possible so that removing a Charge in the field cascades, but a raw delete of an event would silently change the Charge's derived state. Allow a delete only when the parent Charge is gone, if this ever matters (from the #121 review).
- **Office removing a Charge through the field route** (#114): `viewVisit` lets Admin and Office use `DELETE /charges/:id` on an open Visit's unreviewed Charge, which leaves no history. This was already possible with Visit hours (from the #121 review).
- **Archived Item or VAT Code allowed on any line** of an Invoice once one line uses it. Now that lines have ids, narrow it to the line that holds it (from the #122 review).
- **Equipment moved with a corrected Item** (#123): a description or interval counts as "set by hand" when it differs from the old Item's _current_ one, so editing that Item after the install makes an untouched value look manual and it is kept. No test corrects the Item after the Visit is closed. Any service blocks the move, even the installing Visit marking its own new equipment as serviced, so Office can't correct the Item then (from the #125 review).
- **Call-out Fee wording** (ADR 0012): the glossary calls it a price for attending a Visit, while an imported Quote call-out becomes a Job Charge. Revisit if it confuses anyone (from the #131 review).
- **Test file names** (#130): `invoices_from_time_and_materials.spec.ts` (functional and browser) now test Jobs without a Quote; rename them (from the #133 review).
- **Equipment edit lock untested** (#99): only reading the code shows the edit's `FOR UPDATE` against a closing Visit works; no test runs two connections. The race tests also omit the empty form fields the page sends and don't assert the redirect target (from the #104 review).
- **Small leftovers from the #97 review:** the zero-amount Payment test checks the field, not the `amount.positive` message; the `amountRule` docstring line is over 100 characters.
- **Dates rely on the server's time zone:** "today" checks (e.g. a notice date not in the future, not before the upload day) use the process zone, so they hold only with `TZ=Europe/Rome`, which compose, CI and `.env` all set (from the #101 review).
- **Invoice edit page loads every Submission's XML** to work out `hasFile`; select a boolean instead if Invoices accumulate many Submissions (from the #101 review).
- **Invoice list total vs. stored total** (#25): the Invoice list shows the total worked out from the lines next to a payment status based on the stored `total`. They only differ if they drift; issued Invoices could show the stored value (from the #97 review).
- **`DisplayedJobStatus` lives in `app/services`** (#25), not `shared/`, while the stored statuses and the Job list's filters are in `shared/jobs.ts` (#138). Move it there when a page needs it (from the #97 review).
- **Payment dated before the Invoice** (#25): `paidOn` can be earlier than the Invoice's `issuedOn` (an advance paid before issuing is plausible, so decide before refusing it) (from the #97 review).
- **Correction below paid, stock side untested** (#102; dropped by #144: remove when it merges): no test refuses a correction on a Job-less Invoice with Item lines to show stock isn't rebooked and the snapshots stay (the throw precedes `rebookSale` in the transaction) (from the #106 review).
- **"Paid" computed two ways:** `Invoices.save` sums Payments in SQL, `Payments.record` uses the preloaded `invoice.paid`. One shared helper would keep them from drifting (from the #106 review).
- **PDF documents format euro themselves:** `invoice_document.ts` and `quote_document.ts` each build an `Intl.NumberFormat` instead of `formatMoney` from `shared/money.ts`, which itself hard-codes the `'it'` locale (the `LOCALE` constant lives in `inertia/i18n.ts`); fine while there is one language (from the #106 review).
- **Visit team read before the lock** (#93): the edit validator reads "already on the Visit" before `Scheduling.update` locks it, so a stale form submitted just after someone was removed can put them back even if no longer a Technician. Same pattern as for deactivated Technicians; low risk (from the #105 review).
- **Billed amount before the global discount** (#116): a "billed" event records the Charge's part of its line's amount; an Invoice-wide discount isn't spread over the Charges, so their billed amounts can add up to more than the Invoice's taxable amount. Decide with #146, where Credit Notes credit Charges.
- **One draft holds a Charge at a time, by the Job lock** (#116): nothing in the schema stops two drafts' lines linking the same Charge; drafting, saving, finalising and deleting all lock the Job first, and only Charges the Invoice already holds can move between its lines.
- **Backfilled links are matched by description** (#116): the migration links each Charge to the line drafted from it by description, quantity and price. A line Office had edited can't be matched: in a draft its Charge is released, on an issued Invoice it is billed without a line (`invoice_line_id` null) and at the Charge's own value, not the line's (a repriced line). Links are dated `now()`, so a correction made before the migration while a draft held the Charge isn't re-derived when that draft releases it.
- **Deploying #116's migration** (`1761885935209_invoice_line_charges`): finalise or delete open drafts with edited lines first. Their Charges are released by the backfill while the draft still has the lines, so the work could be billed twice.
- **Archiving a VAT Code a rule uses** (#26): the rules quietly fall back to the standard rate (archiving N6.7 makes company building work 22%) and the Admin isn't told; warn on archive, or refuse while rules use it (from the #108 review).
- **Archived VAT Code on new Invoice lines** (#26): the invoice validator lets any line use an archived code as long as another line of the draft already does (`meta.vatCodeIds` comes from the current lines) (from the #108 review).
- **Untranslated structural validation messages:** a malformed VAT rules body gets English messages such as "The rules field must be an array"; the UI can't trigger them (from the #108 review).
- **Admin password reset keeps old sessions** (#32): when the Superuser sets a new password for an Admin, sessions already open with the old one stay valid until they expire. Fine for a lost password; a compromised account would need sessions invalidated.
- **Instance settings not read yet** (#32): polling interval, webhook and public URL are stored for #92 (Invoicetronic) and later work; nothing uses them yet.
- **Secrets in flashed input** (#32): on a validation error, Adonis flashes the request input except `password`, `password_confirmation`, `_csrf` and `_method`, so `invoicetronicApiKey`, `webhookSecret` and camelCase `passwordConfirmation` sit (encrypted) in the session cookie for one request. Exclude them in the exception handler or session config (from the #109 review).
- **Issued Document PDF when Gotenberg is down** (#31): an Issued Document's PDF is rendered and stored right after issuing, then served unchanged, so it keeps the logo and Base Layout of that day. If Gotenberg is down then, the first request for the PDF renders and stores it, with the logo and layout of that later day. Retry the rendering in the background if this matters.
- **Storage in the backups** (#33): the storage directory holds files that exist nowhere else: Issued Document PDFs (stored once and never re-rendered), Item Documents and Visit photos. Backups must include it. A missing Issued Document PDF answers 404 and is logged.
- **Orphan Issued Document PDF** (#31): if the process stops between writing a PDF to storage and recording its path, the file stays with no row pointing to it, and the next request renders and stores another. Harmless; a cleanup sweep of unreferenced files under `issued-documents/` would remove it.
- **Issued Document checks outside the lock** (#31): `TemplateData.resolve` reads the chosen Site, Job and Items, and `DocumentTemplates.current(template)` reads the template version, before `IssuedDocuments.issue` opens its transaction, so a concurrent archive, Job edit or template save can slip in between (a save means the document uses the version before it). Only the template's archive and the original's replacement are checked under lock. Same pattern as "Archived-reference check outside the lock".
- **Replacements and archived records** (#31): a replacement may keep the original's archived Items, but not an archived Site or removed Installed Equipment: Office picks current ones. Extend the exemption if replacing old certificates for since-archived Sites turns out to be common.
- **CI's Gotenberg isn't hardened** (#29): compose.yaml starts Gotenberg with JavaScript disabled and an allow-list (the page and data URIs); CI's service container can't take a command, so tests run against the defaults. Start it with `docker run` in a step if a regression there matters.
- **Item search returns null for an archived VAT Code untested** (#26): the behaviour Invoices without a Job rely on (from the #108 review).
- **Job status needs the billing state** (#75): `deriveJobStatus`'s `billingOpen` defaults to false, so a caller that preloads Visits without the `withBillingState` scope would show a partly invoiced Job as Invoiced or Closed; make it required or fail when `$extras.billing_open` is missing (from the #107 review).
- **A "needs another visit" Visit doesn't keep billing open** (#75): with no follow-up planned yet, a Job whose billed work is all invoiced shows Invoiced or Closed although a return visit is owed; same as before #75, a business choice (see #103) (from the #107 review).
- **Advance deductions' down migration** (#116): rolling back `1761885935210_advance_deductions` sets `deducted_in_id` to the latest Invoice deducting each advance, even a draft, and partial amounts are lost.
- **Deductions and DatiFattureCollegate** (#23): the final Invoice's deduction lines name each Advance Invoice in their description; FatturaPA can also reference them in `DatiFattureCollegate`. Also for the commercialista (#17): a deduction at a rate the final Invoice's work doesn't use leaves a negative `DatiRiepilogo` row (XSD-valid), and the final's global discount applies to the work only, never to the advances taken back (from the #113 review).
- **Template version numbering untested under concurrency** (#29): saves lock the template, so versions don't clash (checked by hand with 8 concurrent saves); no `@committed` test covers it (from the #112 review).
- **No body-format version on templates** (#30): the #112 review suggested one before new node types. #30 only adds to the allow-list (`fieldTable`, property placeholders), so every stored body still validates and renders as before; add a version when a change would alter or drop an existing node.
- **Advance Invoice tests to add** (#23): several advances on one Job, a discount on the advance itself, and the Job list filters with only an advance or with a draft final (from the #113 review).
- **Document texts written in services** (#23): `Acconto – …`, `Detrazione acconto fattura …` (and the earlier rejection note) are Italian strings in services rather than in `resources/lang/it` (from the #113 review).
- **Advances with no Invoice left to take them back** (#23, ADR 0011): a Job with an advance left once nothing is left to bill stays open for billing (no draft can be made). (Resolved by #146: remove when it merges.) It needs a Credit Note (#146) or another Invoice to take it back.
- **Imported hours over 24** (#117): a Quote's labour line imports as one Charge of all its hours, but correcting recorded hours accepts at most 24 per Charge (one day's work, as in the field), so a larger imported quantity can't be corrected as recorded; Office edits what is billed instead, or the limit could follow the Charge's origin.
- **Jobs invoiced from their Quote before #117 look billable again** (ADR 0012): a Job whose Invoice came from its Quote (no Charges held) and that has Charges recorded on its closed Visits now counts those Charges as to bill, so it shows a draft to make and is no longer Invoiced. Only dev and seed data has such Jobs, since invoicing isn't live yet; mark those Charges not billable, or reseed.
- **Importing onto a Visit while it closes is untested under concurrency** (#117): `Quotes.importLines` locks the Visit before checking it is open, as field work does, so a Visit closing at the same moment either takes the imported Items off stock or refuses the import. Tests share one connection, where locks are re-entrant, so none proves it; test it on separate connections with the other locking tests (#19).
- **Browser test log noise:** the browser suite logs "Transaction query already complete" six times while still passing. Pre-existing since before #16; not investigated.
