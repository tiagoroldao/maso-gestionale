# Openapi as SDI intermediary

Automatic SDI Submission and the receiving of Supplier Invoices go through Openapi's SDI API, decided by the business on 2026-10-29 (#92). This replaces ADR 0004's choice of Invoicetronic and keeps its principles:

- **Polling is the source of truth.** An on-premises server may be offline (ADR 0002), so the app asks for outcomes and received files on a schedule (the `sdi` Compose service, `node ace sdi:poll`, every "polling minutes" from Instance settings) and catches up after an outage.
- **Webhooks only trigger an earlier poll.** The webhook is optional, needs a secret and the public URL, and its body is never read.
- **One interface.** Every provider call (send, poll outcomes, receive) sits behind `SdiGateway`, so the provider can be swapped.
- **The app works fully without a connection.** With no token (or manual mode) the manual gateway applies: Office uploads files on the SDI portal and records outcomes by hand, and Supplier Invoices are uploaded as files (#198). Configuring Openapi is an Instance setting, never a requirement.

Sending happens outside the Invoice lock. Confirming marks the Submission "sending" under the lock, sends, then records the result under the lock again. If Openapi refuses the file (a 4xx), nothing was sent and it can be sent again. If the result is unknown (a 5xx, a dropped connection, the process stopping), the Submission stays "sending" and is never sent twice. After a grace period the poller lists the files Openapi holds for the Invoice's date and matches the number from each file's payload. It records the Invoice as sent if found, and otherwise makes it ready to send again.

Legal archiving (_conservazione a norma_) of sent Invoices through the intermediary is an Instance setting, decided by the business on 2026-10-29 (#205): off by default, offered only when the intermediary supports it (`SdiGateway.legalArchiving`; Openapi does, the manual gateway doesn't), and turned off, with a warning, when the Superuser switches to a mode without it. When on, each file is sent with archiving requested, and the Submission records it (`invoice_submissions.legal_archiving`). With Openapi the request is the per-file endpoint `POST /invoices_legal_storage`, not the Business Registry Configuration's `apply_legal_storage` flag, because:

- the spec has no way to change a configuration (only `POST`, `GET` and `DELETE` on `/business_registry_configurations`), so turning the flag on or off from the app would mean deleting and recreating the configuration Openapi's account rests on, which is set up outside the app;
- the flag covers every invoice "sent/received by the fiscal ID" at once, so the app couldn't tell which files went to archiving; for Supplier Invoices too, the app requests archiving per file (#214, below);
- with the endpoint, the request is made, and recorded, per Submission, so the Invoice page shows exactly which files went to archiving, and turning the setting off takes effect on the next send.

If the configuration's `apply_legal_storage` is already on (set by hand at Openapi), Openapi may archive plain sends too: the app neither reads nor changes it.

Received Supplier Invoices are archived through the intermediary too, under the same setting, decided by the business on 2026-10-29 (option B on #214). The gateway says whether it can (`SdiGateway.receivedArchiving`; Openapi does, the manual gateway doesn't). With the setting on, each Supplier Invoice stored, whether received through the intermediary or uploaded by Office, is sent with `POST /supplier_invoice_imports_legal_storage`. The request is per file, since one file may hold several invoices, and each invoice records the state (`supplier_invoices.legal_archiving`), when it changed, and the uuid(s) Openapi answers. The Supplier Invoice page shows them.

- **The XML, not the .p7m.** The spec describes `invoice` as "the base64 encoded invoice XML" and never mentions signed files, so a .p7m is sent as the XML it carries, byte for byte. The original file stays in the app.
- **SDI's identifier instead of the metadata file.** The spec takes the SDI metadata file, or `invoice_file_name` and `sdi_id`. The app doesn't keep metadata files, so it sends the file's name and SDI's identifier. Office's uploads carry no identifier: their archiving is marked failed (`noSdiIdentifier`) until Office enters it on the invoice's page, from the Agenzia delle Entrate portal or the metadata file.
- **The answer is read in both shapes.** The spec shows `{ uuid }`, a string, or an array for a file with several invoices. Openapi's other POSTs answer `{ data: { uuid } }` (sandbox), so the app reads either. The real shape is to confirm under #204.
- **Outside any lock, and never refusing the intake.** The invoice is stored first. The file's rows are then marked "sending" under a lock, the request goes out with no lock held, and the result is recorded under the lock again. A failure (a refusal, no credit, a dropped connection) leaves the invoice stored with its archiving failed and shown. The poller retries failed files on every poll, and Office can send one at once from its page. A send cut off before its answer (the process stopped) is taken as failed after ten minutes and retried, so Openapi could get that file twice.
- **Invoices stored before the setting was on** aren't archived automatically. The Superuser queues them with a one-off action on the Instance page ("Archivia le fatture passive già presenti", confirmed first), and the next poll sends them.

Receiving needs a `supplier-invoice` callback registered at Openapi, decided by the business on 2026-10-29 (option (a) on #92). The app keeps one registered: when Openapi mode is saved in Instance settings, and on the poller's first poll or after a change. It points at the webhook URL, with `Bearer <webhook secret>`, when the webhook is enabled. Otherwise it points at the placeholder `https://invalid.invalid/sdi/webhook`, which can never resolve. Each `POST /api_configurations` replaces the whole configuration, so the app reads it first, writes only when the callback differs, and keeps the other events' callbacks. Polling `GET /invoices?type=1` stays the source of truth.

## Confirmed API facts

From Openapi's official documentation and OpenAPI spec (console.openapi.com/apis/sdi, `oas/en/sdi.openapi.json`, read on 2026-10-29). Where marked **(sandbox)**, checked against the sandbox on 2026-10-29; the recorded responses are in `tests/fixtures/openapi`.

- **Hosts:** production `https://sdi.openapi.it`, sandbox `https://test.sdi.openapi.it`.
- **Authentication:** `Authorization: Bearer <token>`. Tokens are created in Openapi's console (OAuth section) or through its API, with an expiry date and scopes. A refused token answers 401 `{"success":false,"message":"Wrong Token",…}` **(sandbox)**.
- **Errors:** `{ success, message, error, data }`, with 400 (validation), 402 (wallet out of credit), 404 and 422 (malformed XML).
- **A Business Registry Configuration first (sandbox):** until one exists for a fiscal id (`POST /business_registry_configurations`), every invoice call answers 401 `"No business registry configurations have been set up."` (error 661).
- **Sending our own XML:** `POST /invoices` with `Content-Type: application/xml` and the FatturaPA file as the body. The answer is `{"data":{"uuid":…},"message":"Created 1  invoice","success":true}` **(sandbox)**, and Openapi queues the file for SDI. `GET /invoices/{uuid}` then shows `marking: "sent"`, Openapi's own `sdi_file_name` and an `sdi_file_id` **(sandbox)**. Variants add a digital signature (`/invoices_signature`), legal storage (`/invoices_legal_storage`) or both. Openapi acts as the transmitter (its own `IdTrasmittente`), so SDI's file name is Openapi's, not ours.
- **Outcomes, by polling:** `GET /invoices_notifications/{uuid}` lists the notices: NS (rejection, with `lista_errori`), RC (delivered), MC (not delivered), NE/DT (public administration acceptance or lapse), AT (PA not deliverable). Each has `created_at` and `message.identificativo_sdi`. `GET /invoices/{uuid}` also gives the invoice's `marking`. We map NS to rejected, RC to delivered, and MC and AT to not deliverable, dated by the notice's day in Rome. NE and DT wait for public administration invoicing (#56). The notice shape is the spec's: in the sandbox, `POST /simulate/customer-notification` answers "customer-notification sent" but stores nothing for polling. The notices stay empty and `marking` stays `sent`, since the simulation only goes to configured callbacks **(sandbox)**.
- **Finding sent files:** `GET /invoices?type=0` filters by `invoiceDate[after|before]`, `createdAt[…]`, `marking` and `downloaded`. **The `invoiceNumber` filter is ignored (sandbox):** a wrong number still lists the file. Each listed file carries `payload`, the invoice as JSON text with `fattura_elettronica_body[].dati_generali.dati_generali_documento.numero`, so the app filters by date at Openapi and matches the number itself.
- **Paging (sandbox):** list answers carry `page`, `itemsPerPage` (10) and `hasMore`; the app reads pages while `hasMore` is true.
- **Received Supplier Invoices, by polling:** `GET /invoices?type=1` (same filters) lists them, and `GET /invoices_download/{uuid}` with `Accept: application/octet-stream` returns the file as SDI delivered it (XML or .p7m). Receiving needs Openapi's recipient code `JKKZDGR` registered with the Agenzia delle Entrate, a Business Registry Configuration for our fiscal id, and **a `supplier-invoice` callback configuration**. The docs say so ("Invoices will be sent to the specified callback and can then be accessed via GET /invoices"), and the sandbox refuses a simulated Supplier Invoice without one: 500, error 631, "Recipient with fiscal id … is not configured" (428) **(sandbox)**. With no callback, `GET /invoices?type=1` lists nothing **(sandbox)**. Still to confirm live (#204): that an invoice whose callback can't be delivered (the placeholder) stays listable.
- **Sandbox simulation:** `POST /simulate/{type}`, sandbox only. With `supplier-invoice` it takes an invoice as JSON (the buyer's `id_codice` is our fiscal id) and delivers it as received. With `customer-notification` it takes `{ uuid, notification: NS|RC|MC|NE|DT|AT }`. With `legal-storage-receipt` it takes `{ uuid }`. The path is `/simulate/{type}`: the console's pricing page names `POST /simulate-supplier-invoice`, which doesn't exist (a 401 from a gateway) **(sandbox)**.
- **Callbacks:** `POST /api_configurations` with `{ fiscal_id, callbacks: [{ event, url, auth_header, field }] }`, one configuration per fiscal id, each call replacing the last. How `GET /api_configurations` reads it back is unconfirmed: the spec's schema says `callbacks` is an array, its example shows one object, and its list response shows a singular `callback` (with a read-only `provider_uuid`). The app accepts all three, and re-posts the other events' callbacks in the write shape, `{ event, url, auth_header, field }`, without read-only fields. `auth_header` is the full header value (e.g. `Bearer …`). The real shape is to confirm under #204. Events: `supplier-invoice`, `customer-invoice`, `customer-notification`, `legal-storage-missing-vat`, `legal-storage-receipt`. Calls carry `auth_header` (e.g. `Bearer …`) and are not signed. Our webhook accepts the secret in `Authorization`, as is or after `Bearer `.
- **Legal archiving (_conservazione a norma_):** offered by Openapi as a separate, paid option: `apply_legal_storage` on the Business Registry Configuration ("Apply legal storage for invoices sent/received by the fiscal ID"), or the `…_legal_storage` endpoints, through a third-party storage platform. It is not part of plain sending. `POST /invoices_legal_storage` takes the same XML body as `POST /invoices` and answers the same `{ data: { uuid } }`. The storage platform's account is activated by an email Openapi sends when the Business Registry Configuration is created. Openapi reports archiving through the `legal-storage-receipt` and `legal-storage-missing-vat` callbacks (simulated with `POST /simulate/legal-storage-receipt`), and `GET /invoices/{uuid}` carries `legally_stored` and a `preserved_document`. Not checked in the sandbox: no live calls were made for #205.
- **Archiving received invoices (spec only, #214):** `POST /supplier_invoice_imports_legal_storage` ("Import a supplier invoice that was already received from SDI. The invoice will be sent to the legal storage") takes JSON `{ invoice, metadata }` or `{ invoice, invoice_file_name, sdi_id }`, with `invoice` and `metadata` in base64. It answers 201 with `uuid`, one per invoice in the file. `POST /supplier_invoice_imports` is the same without archiving. Not checked in the sandbox: no live calls were made for #214 (#204).
- **Pricing (console, 2026-10-29):** `POST /invoices` €0.070 (from €0.022 with a subscription), €0.105 with legal storage (`POST /invoices_legal_storage`; the OpenAPI spec carries no prices, so the Instance settings hint quotes this list); `GET /invoices_download` €0.001. `GET /invoices` and `GET /invoices_notifications` have 1000 free calls a day each, so the poller only asks about Submissions still waiting.

## Considered Options

- **Invoicetronic** (ADR 0004): replaced by the business's choice of Openapi, for now.
- **Openapi's callbacks as the source of truth:** rejected for the reasons in ADR 0004: an offline server would miss them, and polling endpoints exist for both outcomes and received files.

## Consequences

- Legal archiving is the Superuser's choice (#205): with the setting on, Openapi archives each file sent; with it off, or in manual mode, the app sends with plain `POST /invoices` and archiving stays outside the app (ADR 0002), for example through the Agenzia delle Entrate's free service. Either way the app keeps each file as sent. The same setting covers received Supplier Invoices (#214). The app doesn't follow Openapi's archiving receipts (see `docs/follow-ups.md`).
- The Openapi account is set up once, outside the app: the Business Registry Configuration and the recipient code `JKKZDGR` at the Agenzia delle Entrate. The app keeps the `supplier-invoice` callback registered itself, replacing any `supplier-invoice` callback set by hand.
- Received files are kept in `sdi_received_files` and handed to the Supplier Invoice intake (#198), the same way in as Office's uploads. A `duplicate` refusal counts as already received.
