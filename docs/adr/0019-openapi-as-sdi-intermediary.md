# Openapi as SDI intermediary

Automatic SDI Submission and the receiving of Supplier Invoices go through Openapi's SDI API, decided by the business on 2026-10-29 (#92). This replaces ADR 0004's choice of Invoicetronic and keeps its principles:

- **Polling is the source of truth.** An on-premises server may be offline (ADR 0002), so the app asks for outcomes and received files on a schedule (the `sdi` Compose service, `node ace sdi:poll`, every "polling minutes" from Instance settings) and catches up after an outage.
- **Webhooks only trigger an earlier poll.** The webhook is optional, needs a secret and the public URL, and its body is never read.
- **One interface.** Every provider call (send, poll outcomes, receive) sits behind `SdiGateway`, so the provider can be swapped.
- **The app works fully without a connection.** With no token (or manual mode) the manual gateway applies: Office uploads files on the SDI portal and records outcomes by hand, and Supplier Invoices are uploaded as files (#198). Configuring Openapi is an Instance setting, never a requirement.

Sending happens outside the Invoice lock. Confirming marks the Submission "sending" under the lock, sends, then records the result under the lock again. If Openapi refuses the file (a 4xx), nothing was sent and it can be sent again. If the result is unknown (a 5xx, a dropped connection, the process stopping), the Submission stays "sending" and is never sent twice. After a grace period the poller lists the files Openapi holds for the Invoice's date and matches the number from each file's payload. It records the Invoice as sent if found, and otherwise makes it ready to send again.

Legal archiving (_conservazione a norma_) through the intermediary follows the Openapi account, decided by the business on 2026-10-29 (option A on #204, built in #224). The sandbox showed it is an account setting: `apply_legal_storage` on the Business Registry Configuration, which Openapi sets only when the configuration is created (the spec has no way to change it), and which decides which endpoints Openapi takes. So the app reads it and follows it, and never switches it. (#205 first made it a Superuser switch that sent each file to `POST /invoices_legal_storage`; Openapi refuses that endpoint without the flag, so the switch is gone.)

- **Read, not set.** `SdiGateway.readLegalStorage` reads the flag (Openapi: `GET /business_registry_configurations/{fiscal_id}` → `apply_legal_storage`; the manual gateway never archives). Saving Openapi mode reads it, and the poller reads it when it was never read, then once a day (`LEGAL_STORAGE_REFRESH_HOURS`), into Instance settings (`sdi_legal_storage`, null until read, and when it was read). A new mode, environment or token forgets it until read again. The Instance page shows a status line: active at the intermediary, not active (with how to set it up at Openapi), not yet read, or no intermediary; the reminder to archive elsewhere shows whenever it isn't active.
- **Sending (sandbox, 2026-10-29):** with the flag on, Openapi refuses a plain `POST /invoices` (412, "… Please use: /invoices_legal_storage") and takes `POST /invoices_legal_storage`; with it off, it refuses `/invoices_legal_storage` (412, error 387) and takes `/invoices`. So a file goes to `/invoices_legal_storage` exactly when the flag, as last read, is on, and the Submission records it (`invoice_submissions.legal_archiving`, shown on the Invoice page). A flag not yet read counts as off. If the account changed since it was read, Openapi refuses the file (nothing is sent); a refused send reads the flag again, so sending again follows it.
- **Received through Openapi: archived on receipt (sandbox, 2026-10-29).** A Supplier Invoice simulated for a registration with the flag was listed with `legally_stored: true` and a `preserved_document` within a second. So the app never imports those files: each invoice records its archiving as `automatic` when the flag was on as it arrived.

Supplier Invoices Office uploads never went through Openapi, so they are imported for archiving, decided by the business on 2026-10-29 (option B on #214), but only when the flag is on: each uploaded file is sent with `POST /supplier_invoice_imports_legal_storage`, which Openapi refuses without the flag (403, error 456, "Please use /supplier_invoice_imports …"). With the flag it is not yet confirmed: `node ace sdi:sandbox-check` checks it against the `--legal-storage-fiscal-id` registration (check 12, below). The request is per file, since one file may hold several invoices, and each invoice records the state (`supplier_invoices.legal_archiving`), when it changed, and the uuid(s) Openapi answers. The Supplier Invoice page shows them.

- **The XML, not the .p7m.** The spec describes `invoice` as "the base64 encoded invoice XML" and never mentions signed files, so a .p7m is sent as the XML it carries, byte for byte. The original file stays in the app.
- **SDI's identifier instead of the metadata file.** The spec takes the SDI metadata file, or `invoice_file_name` and `sdi_id`. The app doesn't keep metadata files, so it sends the file's name and SDI's identifier. Office's uploads carry no identifier: their archiving is marked failed (`noSdiIdentifier`) until Office enters it on the invoice's page, from the Agenzia delle Entrate portal or the metadata file. It is kept on the invoice only once Openapi takes the file, so a wrong one can be corrected.
- **The answer is read in both shapes.** The spec shows `{ uuid }`, a string, or an array for a file with several invoices. Openapi's other POSTs answer `{ data: { uuid } }` (sandbox), so the app reads either. The real shape is to confirm under #204.
- **Outside any lock, and never refusing the intake.** The invoice is stored first. The file's rows are then marked "sending" under a lock, the request goes out with no lock held, and the result is recorded under the lock again. A failure (a refusal, no credit, a dropped connection) leaves the invoice stored with its archiving failed and shown. The poller retries failed files whose identifier is known on every poll, and Office can send one at once from its page. A send cut off before its answer (the process stopped) is taken as failed after ten minutes and retried, so Openapi could get that file twice.
- **Uploads stored before the flag was on** (or before the app followed it) aren't archived automatically. The Superuser queues them with a one-off action on the Instance page ("Archivia le fatture passive caricate a mano già presenti", confirmed first), and the next poll sends them. Files received through Openapi are never queued.

Receiving needs a `supplier-invoice` callback registered at Openapi, decided by the business on 2026-10-29 (option (a) on #92). The app keeps one registered: when Openapi mode is saved in Instance settings, and on the poller's first poll or after a change. It points at the webhook URL, with `Bearer <webhook secret>`, when the webhook is enabled. Otherwise it points at the placeholder `https://invalid.invalid/sdi/webhook`, which can never resolve. Each `POST /api_configurations` replaces the whole configuration, so the app reads it first, writes only when the callback differs, and keeps the other events' callbacks. Polling `GET /invoices?type=1` stays the source of truth, and option (a) holds **(sandbox, 2026-10-29)**: with the placeholder, a received invoice is still listed, only later. An unreachable callback delays receipt by minutes (about 7 in the sandbox), against seconds with a reachable one; the poller catches it on a later poll.

## Confirmed API facts

From Openapi's official documentation and OpenAPI spec (console.openapi.com/apis/sdi, `oas/en/sdi.openapi.json`, read on 2026-10-29). Where marked **(sandbox)**, checked against the sandbox on 2026-10-29; the recorded responses are in `tests/fixtures/openapi`.

- **Hosts:** production `https://sdi.openapi.it`, sandbox `https://test.sdi.openapi.it`.
- **Authentication:** `Authorization: Bearer <token>`. Tokens are created in Openapi's console (OAuth section) or through its API, with an expiry date and scopes. A refused token answers 401 `{"success":false,"message":"Wrong Token",…}` **(sandbox)**.
- **Errors:** `{ success, message, error, data }`, with 400 (validation), 402 (wallet out of credit), 404 and 422 (malformed XML).
- **A Business Registry Configuration first (sandbox):** until one exists for a fiscal id (`POST /business_registry_configurations`), every invoice call answers 401 `"No business registry configurations have been set up."` (error 661).
- **Sending our own XML:** `POST /invoices` with `Content-Type: application/xml` and the FatturaPA file as the body. The answer is `{"data":{"uuid":…},"message":"Created 1  invoice","success":true}` **(sandbox)**, and Openapi queues the file for SDI. `GET /invoices/{uuid}` then shows `marking: "sent"`, Openapi's own `sdi_file_name` and an `sdi_file_id` **(sandbox)**. Variants add a digital signature (`/invoices_signature`), legal storage (`/invoices_legal_storage`) or both. Openapi acts as the transmitter (its own `IdTrasmittente`), so SDI's file name is Openapi's, not ours.
- **Outcomes, by polling:** `GET /invoices_notifications/{uuid}` lists the notices: NS (rejection, with `lista_errori`), RC (delivered), MC (not delivered), NE/DT (public administration acceptance or lapse), AT (PA not deliverable). Each has `created_at` and `message.identificativo_sdi`. `GET /invoices/{uuid}` also gives the invoice's `marking`. We map NS to rejected, RC to delivered, and MC and AT to not deliverable, dated by the notice's day in Rome. NE and DT wait for public administration invoicing (#56). **Outcomes are stored for polling (sandbox, 2026-10-29):** a notice simulated with `POST /simulate/customer-notification` is listed at `GET /invoices_notifications/{uuid}`, and the gateway reads a simulated RC as delivered. (An earlier reading, that the sandbox stored nothing and only called the callbacks, was wrong.)
- **Finding sent files:** `GET /invoices?type=0` filters by `invoiceDate[after|before]`, `createdAt[…]`, `marking` and `downloaded`. `invoiceDate[after|before]` and `createdAt[after]` are honoured, lists come newest first, and a queued sent file is found by its date plus the number in its `payload` while `marking: sent` **(sandbox, 2026-10-29)**. **The `invoiceNumber` filter is ignored (sandbox):** a wrong number still lists the file. Each listed file carries `payload`, the invoice as JSON text with `fattura_elettronica_body[].dati_generali.dati_generali_documento.numero`, so the app filters by date at Openapi and matches the number itself. **A sent file is listed by `invoiceDate` only after a lag (145 s seen in the sandbox, 2026-10-29, #204):** the grace period before the poller settles an unknown send (`SENDING_GRACE_MINUTES`, 10) must stay well above it, or a file that did arrive would read as never sent and go twice.
- **Paging (sandbox):** list answers carry `page`, `itemsPerPage` (10) and `hasMore`; the app reads pages while `hasMore` is true.
- **Received Supplier Invoices, by polling:** `GET /invoices?type=1` (same filters) lists them, and `GET /invoices_download/{uuid}` with `Accept: application/octet-stream` returns the file as SDI delivered it (XML or .p7m). Receiving needs Openapi's recipient code `JKKZDGR` registered with the Agenzia delle Entrate, a Business Registry Configuration for our fiscal id, and **a `supplier-invoice` callback configuration**. The docs say so ("Invoices will be sent to the specified callback and can then be accessed via GET /invoices"), and the sandbox refuses a simulated Supplier Invoice without one: 500, error 631, "Recipient with fiscal id … is not configured" (428) **(sandbox)**. With no callback, `GET /invoices?type=1` lists nothing **(sandbox)**. With a reachable callback, a simulated Supplier Invoice is listed within seconds, with `marking: received` and `downloaded_at` set; with the undeliverable placeholder it is listed too, after about 7 minutes (72 polls of about 6s), also with `downloaded_at` set **(sandbox, 2026-10-29)**. So `downloaded` and `downloaded_at` record Openapi's hand-over to the callback, delivered or not, not the app's download: the poller never filters on them.
- **Sandbox simulation:** `POST /simulate/{type}`, sandbox only. With `supplier-invoice` it takes an invoice as JSON (the buyer's `id_codice` is our fiscal id) and delivers it as received. With `customer-notification` it takes `{ uuid, notification: NS|RC|MC|NE|DT|AT }`. With `legal-storage-receipt` it takes `{ uuid }`. The path is `/simulate/{type}`: the console's pricing page names `POST /simulate-supplier-invoice`, which doesn't exist (a 401 from a gateway) **(sandbox)**.
- **Callbacks:** `POST /api_configurations` with `{ fiscal_id, callbacks: [{ event, url, auth_header, field }] }`, one configuration per fiscal id, each call replacing the last. The spec's schema says `callbacks` is an array, its example shows one object, and its list response shows a singular `callback` (with a read-only `provider_uuid`). **The sandbox reads back one item per callback, each with a singular `callback` object and its `fiscal_id` (2026-10-29).** The app accepts all three shapes, and re-posts the other events' callbacks in the write shape, `{ event, url, auth_header, field }`, without read-only fields. `auth_header` is the full header value (e.g. `Bearer …`). The `fiscal_id` filter is validated: a fiscal id without a Business Registry Configuration answers 404 "Fiscal ID not found or not registered" (error 420) **(sandbox)**. Events: `supplier-invoice`, `customer-invoice`, `customer-notification`, `legal-storage-missing-vat`, `legal-storage-receipt`. Calls carry `auth_header` (e.g. `Bearer …`) and are not signed. Our webhook accepts the secret in `Authorization`, as is or after `Bearer `.
- **Legal archiving (_conservazione a norma_):** offered by Openapi as a separate, paid option: `apply_legal_storage` on the Business Registry Configuration ("Apply legal storage for invoices sent/received by the fiscal ID"), or the `…_legal_storage` endpoints, through a third-party storage platform. It is not part of plain sending. `POST /invoices_legal_storage` takes the same XML body as `POST /invoices` and answers the same `{ data: { uuid } }`. The storage platform's account is activated by an email Openapi sends when the Business Registry Configuration is created. Openapi reports archiving through the `legal-storage-receipt` and `legal-storage-missing-vat` callbacks (simulated with `POST /simulate/legal-storage-receipt`), and `GET /invoices/{uuid}` carries `legally_stored` and a `preserved_document`. **For a registration without `apply_legal_storage`, `POST /invoices_legal_storage` answers 412 "Your current configuration for this fiscal_id does not allow requests on this endpoint. Please use: /invoices" (error 387) (sandbox, 2026-10-29):** legal storage needs the flag on the registration, which Openapi sets only when the registration is created (the spec has no way to change it). **With the flag (sandbox, 2026-10-29, #223 checks 9 to 11):** plain `POST /invoices` answers 412 "… Please use: /invoices_legal_storage"; `POST /invoices_legal_storage` is taken, with `legally_stored` false right after (archiving follows later); a received invoice is `legally_stored` with a `preserved_document` within a second of being listed. The app reads the flag from `GET /business_registry_configurations/{fiscal_id}` as `{ data: { apply_legal_storage } }` (or a list of one), the shape the sandbox check reads; the app's own read is still to confirm.
- **Archiving received invoices (spec only, #214):** `POST /supplier_invoice_imports_legal_storage` ("Import a supplier invoice that was already received from SDI. The invoice will be sent to the legal storage") takes JSON `{ invoice, metadata }` or `{ invoice, invoice_file_name, sdi_id }`, with `invoice` and `metadata` in base64. It answers 201 with `uuid`, one per invoice in the file. `POST /supplier_invoice_imports` is the same without archiving. **For `02903752463`, a registration without `apply_legal_storage`, the sandbox refused a received file with 403 "Please use /supplier_invoice_imports for importing invoice to legal storage for: 02903752463" (error 456) (2026-10-29).** With the flag it is untested (check 12).
- **Pricing (console, 2026-10-29):** `POST /invoices` €0.070 (from €0.022 with a subscription), €0.105 with legal storage (`POST /invoices_legal_storage`; the OpenAPI spec carries no prices, so the Instance settings hint quotes this list); `GET /invoices_download` €0.001. `GET /invoices` and `GET /invoices_notifications` have 1000 free calls a day each, so the poller only asks about Submissions still waiting.

## Considered Options

- **Invoicetronic** (ADR 0004): replaced by the business's choice of Openapi, for now.
- **Openapi's callbacks as the source of truth:** rejected for the reasons in ADR 0004: an offline server would miss them, and polling endpoints exist for both outcomes and received files.

## Consequences

- Legal archiving is chosen when the Openapi account is set up, outside the app (#224): with `apply_legal_storage`, Openapi archives each file sent and received, and the uploads the app sends it; without it, or in manual mode, archiving stays outside the app (ADR 0002), for example through the Agenzia delle Entrate's free service, and the Instance page says so. Either way the app keeps each file as sent or received. Turning it on for an existing account means asking Openapi, since the flag is set only when the configuration is created. The app doesn't follow Openapi's archiving receipts (`legally_stored`; see `docs/follow-ups.md`).
- The Openapi account is set up once, outside the app: the Business Registry Configuration and the recipient code `JKKZDGR` at the Agenzia delle Entrate. The app keeps the `supplier-invoice` callback registered itself, replacing any `supplier-invoice` callback set by hand.
- Received files are kept in `sdi_received_files` and handed to the Supplier Invoice intake (#198), the same way in as Office's uploads. A `duplicate` refusal counts as already received.
